# MachSight Canonical Telemetry Contract

**Contract Version**: `2`  
**Status**: Formal Standard  
**Document Owner**: Architecture & Telemetry Working Group  

---

## 1. Executive Summary & Core Architectural Principle

> **"MachSight must consume machine telemetry, not simulator telemetry or hardware telemetry."**

The MachSight diagnostic platform evaluates the operational health, degradation, and mechanical anomalies of RC machine assets. Downstream diagnostic pipelines, anomaly detection models (e.g. Isolation Forests), rule-based health evaluators, and visualizers must remain completely agnostic to whether data was generated by:
- The physics-inspired software digital twin (`SimulatorTelemetrySource`),
- Synthetic mock hardware testing adapters (`MockHardwareTelemetrySource`), or
- Real embedded physical microcontrollers (`BluetoothTelemetrySource` on ESP32).

Every acquisition source MUST translate raw, hardware-specific signals and units into this canonical telemetry contract before transmission across the system boundary.

## 4. Timestamp Semantics & Clock Discipline

1. **Epoch & Precision**: All timestamps MUST be floating-point numbers representing UTC seconds elapsed since the Unix Epoch (`1970-01-01T00:00:00Z`). Millisecond or microsecond sub-second resolution is expected.
2. **Measurement vs. Transmission Timestamps**:
   - `timestamp`: Represents the packet assembly and dispatch timestamp. Always present.
   - `measurement_timestamp`: Represents the exact physical sensor sampling instant on the microcontroller ADC / timer interrupt. Useful for network jitter compensation.
3. **Embedded Clock Synchronization & Drift**:
   - When the hardware microcontroller (e.g. ESP32) lacks an RTC battery or NTP connectivity, it maintains elapsed time via internal monotonic microsecond timers (`esp_timer_get_time()`).
   - The hardware adapter bridge (e.g. the host Python process communicating over Bluetooth) is responsible for calibrating the offset between the microcontroller's internal timer and host UTC epoch time upon initial handshake.
   - Downstream consumers MUST NOT reject packets with sub-millisecond clock jitter, but SHOULD flag persistent clock drift exceeding $\pm 2.0$ seconds.

---

## 5. Sequence Semantics, Loss Detection & Duplicate Filtering

1. **Session Scope**: Sequence numbers are non-negative integers strictly scoped to a unique `session_id`.
2. **Monotonicity**: Each transmitted telemetry packet MUST increment `sequence` by $+1$.
3. **Packet Loss Detection**:
   - When a consumer receives sequence $N+K$ (where $K > 1$) directly after $N$, exactly $K-1$ packets were lost in transit:
     $$\text{Missing Packets} = \{N+1, N+2, \dots, N+K-1\}$$
   - Sequence loss triggers transport-layer degradation accounting without falsely accusing physical sensors of dropping data.
4. **Duplicate Detection**: If a packet arrives with $\text{sequence} \le \text{last\_seen\_sequence}$ within the same `session_id`, it is flagged as a duplicate or out-of-order retransmission and discarded.
5. **Session Reset**: When a device reboots or reconnects, a new `session_id` is assigned and `sequence` resets to $0$ or $1$. Consumers MUST reset their sequence trackers upon observing a changed `session_id`.

## 6. Sensor Quality & Health Metadata (`sensor_status`)

To enable diagnostic systems to distinguish real mechanical failure (e.g. a locked rotor) from electrical sensor defects (e.g. a loose ADC wire), each sensor includes an acquisition status flag:

| Status Code | Meaning | Diagnostic System Interpretation |
|---|---|---|
| `"ok"` / `"good"` | Sensor reading is valid, fresh, and within physical tolerances. | Trust sensor value completely for anomaly detection. |
| `"stale"` | Reading unchanged across multiple sampling periods while vehicle is moving. | Sensor may be frozen or mechanically stuck. |
| `"dropped"` | Sensor sample timed out or returned CRC/parity error. | Impute value or treat as momentary packet dropout. |
| `"degraded"` | High noise or intermittent pulse irregularity detected. | Increase uncertainty interval in diagnostic filters. |
| `"invalid"` | Value exceeds electrical or sensor range (e.g. negative current). | Sensor malfunction or wiring short-circuit. |
| `"disconnected"` | Hardware bus (I2C/ADC/Echo) failed to acknowledge. | Sensor hardware offline. Do not misdiagnose as car breakdown. |

## 7. Source Provenance Rules

The `source` metadata block identifies the transport and acquisition origin:
- `source_type`: `"simulator"` \| `"hardware"` \| `"mock_hardware"`
- `device_id`: Device identifier
- `transport`: `"websocket"` \| `"bluetooth"` \| `"serial"` \| `"simulation"`

### Architectural Non-Branching Invariant
> **Downstream diagnostic models and anomaly detection pipelines MUST NOT branch their diagnostic conclusions based on `source.source_type`.**

The presence of `source_type: "hardware"` versus `source_type: "simulator"` is informational for logging, telemetry routing, and audit records. Machine fault detection algorithms must evaluate only physical state (`sensors`, `operating_state`, `sensor_status`).

## 8. Hardware Sensor Name & Unit Mapping Rules

Hardware-specific register names, pin numbers, and raw sensor codes MUST NEVER leak into the canonical contract:

| Physical Component | Raw Microcontroller Signal | Canonical Telemetry Field | Canonical Unit |
|---|---|---|---|
| HC-SR04 Ultrasonic Sensor | Echo pin pulse duration in $\mu s$ or distance in $mm$ | `sensors.distance_cm` | Centimeters ($cm$) |
| INA219 Current Sensor | Shunt ADC register in $mA$ | `sensors.current_a` | Amperes ($A$) |
| Optical Wheel Encoder | Slotted disk pulse count per second | `sensors.wheel_rpm` | Revolutions / Min ($RPM$) |
| LiPo Battery Divider | Raw ADC 12-bit counts | `battery_voltage_v` (backend flat format) | Volts ($V$) |

## 9. Contract Schema Versioning Strategy

The telemetry contract follows strict versioning rules:

1. **MAJOR Version Changes** (e.g. `schema_version: 1` $\to$ `2` $\to$ `3`):
   - Breaking field deletions, renamings, or physical unit changes (e.g. changing $cm$ to meters).
   - Downstream consumers MUST explicitly support the major version or cleanly reject the packet.
2. **MINOR Additive Changes**:
   - Introduction of optional metadata fields or new sensor signals.
   - Existing consumers MUST ignore unknown additive fields without failing (`extra="ignore"` or tolerant deserialization).
3. **PATCH Changes**:
   - Clarifications in documentation, updated range limits, or stricter validation rules.

## 10. Backward Compatibility: MachSight Backend Flat Format

For seamless integration with existing MachSight ingestion endpoints, the canonical `TelemetryMessage` provides `.to_machsight_dict()` which emits the flat structure:

```json
{
  "schema_version": 2,
  "machine_id": "rc-car-01",
  "car_id": "rc-car-01",
  "asset_type": "rc_vehicle",
  "timestamp": 1727700000.125,
  "mode": "forward",
  "pwm_command": 175,
  "distance_cm": 82.4,
  "current_a": 2.73,
  "rpm": 312.6
}
```

Notice:
- `sensors.wheel_rpm` maps to the legacy MachSight field `"rpm"`.
- `sensors.current_a` maps to `"current_a"`.
- `sensors.distance_cm` maps to `"distance_cm"`.
- Ground-truth physics variables (`mechanical_load`, `wheel_slip`, `true_velocity_mps`) are **strictly excluded**.
